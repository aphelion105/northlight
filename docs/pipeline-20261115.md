## Keep fusion; remove useless texture reads

The old log shows a smaller sum of RemovalSmooth and TemporalLight than the
new log's merged TemporalLight. That initially suggested reverting fusion.
Controlled same-input GPU A/B did **not** support that conclusion: the fused
path remained faster on the authored cases and saved capture. Fusion stays
enabled. The earlier cross-run inference must not be cited as a regression.

`smoothRemoval` previously flattened its `w > 0` guard. This performed scene,
AO and baseline-light texture reads even when the tap could not contribute.
The DXVK 3.1.1 variant now uses dynamic branching. Every accepted tap, the 24-tap spiral,
normal/depth thresholds, accumulation order, temporal history, precision and
resolution remain the same. Other backends and the separate diagnostic path
retain their previous bytecode. The new fused shader uses 408 static slots and 20 temporaries
(previously 402 and 21); static instruction count alone does not predict the
cost of texture work inside a loop.

The longer tests exposed a backend difference: DXVK 2 regressed on coherent
and fully shadowed inputs and the saved capture. The loader therefore enables
`TemporalLightMergedZeroWeight` only for the **actually loaded** DXVK `v3.1.1`,
not a requested backend name. Unknown versions, native D3D9 and loader fallback
keep `TemporalLightMerged`. Only one shader is created and executed normally;
failure to create the optimized shader falls back to the original fused one.
Reset permits a retry. `BACKEND_WORK temporalZeroWeight` and sampled
`WORLD temporal zeroWeight` distinguish permission from actual use.

A second experiment rejected taps earlier using visibility alone. It improved
the fragmented-shadow fixture but regressed the fully shadowed fixture by
about 8%, so it was not adopted. The production change branches only after
the complete existing weight calculation.

The comparator now accepts `--reference-fused` and requires **byte-exact**
RGBA history images for that mode. Added timing cases cover fully lit,
coherent-shadow and fully shadowed images, alongside the fragmented fixture.
The older two-pass/fused comparison retains its explicit FP16 tolerance.
Saved capture replay still uses authored history and neutral authored AO;
it is not a complete replay of the live game frame.

Final production-bytecode runs are `production-dxvk3-ab/` and
`production-dxvk3-aa/`. Both use 16 ABBA blocks, 128 draws per timed batch,
and longer warmup. All fourteen image sequences are byte-exact.

Neither this table nor the mixed gameplay logs prove a game FPS increase.

## Split the unmeasured end of the frame

The existing asynchronous frame profiler now distinguishes `LateScene`,
`HDRPrepare`, `HDRResolve`, `HDRExposure`, `HDRBloom` and `HDROutput`.
The remaining `tail` follows output conversion. These are command-stream
intervals, including stalls, not independent CPU times. Disabled stages can
have an almost-zero interval. Failed passes do not report successful output.

Marks are supplied only on already sampled frames; they use the existing
nonblocking query ring. There are no extra rendering passes, resources for
images, flushes or waits. The frame profiler has room for twelve marks.

Do not remove the final HDR resolve based on its appearance alone: native
late geometry still uses the composed MSAA target, while HDR postprocessing
must read a separate sampleable texture. Eliminating it requires a proven
handoff of the final scene writer, not merely reusing a texture pointer.

## Validation

`verify_hdr_frame_gpu.py` checks 2,909 cases on each of DXVK 2 and DXVK 3.
The added marker oracle uses real timestamp queries and compares every output
byte with profiling disabled for 16 exposure/world-validity/bloom combinations.
Failure injection checks that aborted passes never emit `HDROutput` and still
restore device state.

Use the source, architecture and lighting-composite suites after the production
build. `test_removal_zero_weight_gpu.py` compares the shipped pre-change shader
from `b725ae54` against current production bytecode across moving history,
cuts, normal/depth boundaries, fog, sky and no-source cases. Performance runs
use `test_removal_temporal_merge_gpu.py --benchmark --timing-batch 128
--reference-fused ... --candidate shaders/compiled/TemporalLightMergedZeroWeight.bin`,
with `--control` for A/A and `--backend` for the second DXVK version. The actual
renderer test also forces both fused variants on each of DXVK 3, DXVK 2 and
native D3D9 to check image/state equivalence, resize/reset and creation failure;
the loader policy test verifies the production selection separately.

Forever remains open throughout the GPU checks, as requested. Component
timings do not establish a gameplay FPS improvement. The next live run must
confirm the effect cost and use the new HDR intervals to locate the remaining
frame-tail bottleneck.
