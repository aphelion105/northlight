# Using the client's prepared M2 draw data

The installed 3.3.5a client already identifies the model, mesh section, material and current bone selection as it draws. Northlight can use that information on the game thread, before D3D9 submission. The largest opportunity in the stationary Northrend recording is the CPU work to identify and prepare each model draw. The warm paths already reuse vertex and index data.

## Matched gameplay

The two recordings used the same camera at (5846.43, 603.90, 658.45), facing (0.6830, 0.6725, −0.2850), at 3840×2160 with 2× MSAA. Each build contributed the last two complete, focused 120-frame windows before switching off, four after switching off, and two after switching back on. Windows after a switch started at least two seconds later. Enabled windows required matching camera observations throughout. Frame times are averages over 480 frames per state. All four also reported zero normal UP bytes. CPU operations on cached vertices still occurred. For example, frame 2413 used the 8,192-vertex pose allowance and evaluated 603 local pose envelopes. ## What the engine actually provides

* **Scene selection.** `CM2Scene::Draw` passes the existing element array and pass-specific index sequence to the renderer. Pass zero also has a separate doodad sequence. Each ordinary element identifies an instance, a material batch, a skin section and shader permutations. The engine's ordered dispatch distinguishes ordinary batches, projected batches, grouped doodads, ribbons, particles and callbacks. The M2 list covers models. Terrain and WMO geometry have their own owners. [Scene and element fields](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Scene.h#L30-L71) · [Pass submission](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Scene.cpp#L2289-L2318)
* **Geometry and pose.** The stock shader path binds shared geometry and selects the current section's bone combination from the animated instance. It packs three float4 rows per bone starting at vertex register c31. The actual indexed draw uses the section's index range and vertex range. This supplies the information needed to reproduce deformation on the GPU. An ordinary shader-skinned draw need not have a CPU array of posed vertices. Grouped doodads can pack several instances' palettes into one draw. [Vertex binding](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/CM2SceneRender.cpp#L181-L213) · [Ordinary batch](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/CM2SceneRender.cpp#L454-L513) · [Grouped doodads](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/CM2SceneRender.cpp#L697-L740)
* **Bounds.** The current model box may come from an animation sequence and instance transform. Per-section `GetRegionBounds` walks vertices and blends bone matrices. Calling it once per draw would reintroduce the scan. Sequence bounds can first be compared with actual posed geometry across animations and attachments before using them to discard visible work. [Model box](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Model.cpp#L988-L1048) · [Section computation](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Model.cpp#L3009-L3069)
* **WarcraftXL.** v1.1 supplies typed skin, section and batch layouts and declares skin-finalize, instance-palette and batch-draw events. The batch notification is issued after the draw and carries its D3D arguments plus the model. The explicit one-shot interface also wraps a D3D indexed draw. The M2 extension owns this path. v1.2 explicitly attributes the palette and batch events to the external producer. Subscribing to the core's event names alone does not establish delivery or recover the section before Northlight records the draw. [v1.1 skin layout](https://github.com/WarcraftXL/core/blob/f39aa1c9f2020d0968def3de895283cf0412e7cd/src/game/M2.hpp#L69-L92) · [Batch arguments](https://github.com/WarcraftXL/core/blob/f39aa1c9f2020d0968def3de895283cf0412e7cd/src/engine/events/Event.hpp#L133-L148) · [One-shot interface](https://github.com/WarcraftXL/core/blob/f39aa1c9f2020d0968def3de895283cf0412e7cd/include/wxl/M2DrawApi.h#L22-L31) · [v1.2 event ownership](https://github.com/WarcraftXL/core/blob/2a9132b0306380b632e51b594b8c066a9af0af24/include/wxl/events/Events.def#L29-L56)
* **Native Vulkan.** Esteria's Gx device resolves bound vertex and index pools, reads the batch range, flushes current shader registers, builds bindings and submits a draw. Its interface lives inside a rebuilt client. The installed client calls D3D9 and uses DXVK. The semantic inputs are available above either backend. Generating matching per-pixel normal, depth and alpha coverage remains a separate render operation. The existing Northlight MSAA fusion experiment has image and timing results relevant to changing that operation. [Vulkan draw](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Gx/CGxDeviceVulkan/CGxDeviceVulkanDraw.cpp#L74-L201) · [Northlight MSAA experiment](msaa-worldnormals-fusion-20261114.md)

## Verification against the installed game

Offline disassembly of the installed PE32 `Wow.exe` (3.3.5.12340, SHA-256 `99155d4d6ed4937a5ab1f5972d11e8605b986561b9f08686ab66af2c582194ec`) confirmed two scene-to-dispatch calls, separate ordinary and grouped-doodad branches, current-element batch/section loads, the bone-combination lookup into the instance palette, the c31 upload and the indexed section fields at Gx submission. The five byte regions inspected also matched the installation's `Wow_original.exe`. This verifies selected code paths on disk. The log contains aggregate draw counters and no per-draw native model/section IDs, so it cannot establish runtime matching coverage.

## First integration for the existing client

1. Observe ordinary opaque M2 batches on the game thread as the engine submits them. Reuse the existing CPU/GPU source identity and buffer generation for the active section. Cache immutable section metadata per loaded skin/LOD, and share the exact emitted palette rows per pose and bone combination. This naturally follows visibility and draw order during the engine's own traversal. Reading the scene again at frame end would lose that ordering and repeat work.
2. Attach the metadata reference to the **specific device draw** as the command producer records it. Include the pass, generation and section range. Transfer owned data or a frame-lifetime reference across the queue. The live log used separate game and replay threads with two frames ahead configured. A later read of an engine pointer can observe a recycled model, a newer pose or another pass. The existing producer already associates camera/light snapshots with a draw ordinal. [Snapshot capture](../src/stream/game_snapshot.h) · [Per-draw capture](../src/proxy/renderer.cpp)
3. First run the association alongside the existing path and compare section draw arguments, buffer identity, palette rows and actual material/alpha state for the same command. Count eligible, matched, ambiguous and fallback draws. Grouped instances, UP/dynamic geometry, projected passes and missing metadata keep their existing capture until separately supported. An off-screen caster can still affect a visible receiver, so the camera pass's visible list alone cannot establish shadow eligibility.
4. First consume matched records in material admission and model-normal packet preparation. Compare producer and replay CPU time, total frame time, normal/material images and actual GPU submissions on the same input. This measures whether CPU work disappears or moves between threads. Reducing the remaining normal draws requires a compatible GPU pass or batching improvement in addition to the CPU integration.

## Implemented for ordinary opaque M2

The command-stream producer now recognizes the indexed shader batch in build 12340. It checks three executable code regions at startup. On submission it checks both callers, the scene pass and material, active D3D bindings, alpha state and the final draw range including Gx pool offsets. A match adds 16 bytes to that draw. They describe the instance, section, material and bone selection. Replay treats the identity words as opaque. The existing ordered shader-constant commands own the actual palette values. Other draws retain their ordinary D3D packet. [Client adapter](../src/stream/m2_draw_12340.h)

The material cache can reuse a posed section bound across draws when the immutable mesh owner, shader, declaration, camera basis and every palette row used by the envelope still match. Storage is charged to the existing 8 MiB bounds budget. A repeated pose can also satisfy a coarse material range query. For normals, a draw can copy constants directly from the material calculation when the requested span is covered and the device mirror certifies its write generation under the draw lock. Queued packets retain their own storage. [Material bounds](../src/water/auto_displacement_renderer.h) · [Normal packets](../src/proxy/model_normal_renderer.h)

With diagnostics enabled, `NATIVE_M2` reports producer matches, rejected ranges and sampled comparisons between the engine matrices and the D3D palette. `NATIVE_M2_MATERIAL` reports local evaluations, reused bounds and reused range queries. `NATIVE_M2_NORMALS` counts reused constant spans, their size in float4 registers and sampled comparisons against a fresh device read. Whole-frame cost and GPU submissions still come from the existing frame and model-normal reports.
