# Using the client's prepared M2 draw data

The installed 3.3.5a client already identifies the model, mesh section, material and current bone selection as it draws. Northlight can use that information on the game thread, before D3D9 submission. The largest opportunity in the stationary Northrend recording is the CPU work to identify and prepare each model draw. The warm paths already reuse vertex and index data.

## What the engine actually provides

* **Scene selection.** `CM2Scene::Draw` passes the existing element array and pass-specific index sequence to the renderer. Pass zero also has a separate doodad sequence. Each ordinary element identifies an instance, a material batch, a skin section and shader permutations. The engine's ordered dispatch distinguishes ordinary batches, projected batches, grouped doodads, ribbons, particles and callbacks. The M2 list covers models. Terrain and WMO geometry have their own owners. [Scene and element fields](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Scene.h#L30-L71) · [Pass submission](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Scene.cpp#L2289-L2318)
* **Geometry and pose.** The stock shader path binds shared geometry and selects the current section's bone combination from the animated instance. It packs three float4 rows per bone starting at vertex register c31. The actual indexed draw uses the section's index range and vertex range. This supplies the information needed to reproduce deformation on the GPU. An ordinary shader-skinned draw need not have a CPU array of posed vertices. Grouped doodads can pack several instances' palettes into one draw. [Vertex binding](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/CM2SceneRender.cpp#L181-L213) · [Ordinary batch](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/CM2SceneRender.cpp#L454-L513) · [Grouped doodads](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/CM2SceneRender.cpp#L697-L740)
* **Bounds.** The current model box may come from an animation sequence and instance transform. Per-section `GetRegionBounds` walks vertices and blends bone matrices. Calling it once per draw would reintroduce the scan. Sequence bounds can first be compared with actual posed geometry across animations and attachments before using them to discard visible work. [Model box](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Model.cpp#L988-L1048) · [Section computation](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Model2/M2Model.cpp#L3009-L3069)
* **WarcraftXL.** v1.1 supplies typed skin, section and batch layouts and declares skin-finalize, instance-palette and batch-draw events. The batch notification is issued after the draw and carries its D3D arguments plus the model. The explicit one-shot interface also wraps a D3D indexed draw. The M2 extension owns this path. v1.2 explicitly attributes the palette and batch events to the external producer. Subscribing to the core's event names alone does not establish delivery or recover the section before Northlight records the draw. [v1.1 skin layout](https://github.com/WarcraftXL/core/blob/f39aa1c9f2020d0968def3de895283cf0412e7cd/src/game/M2.hpp#L69-L92) · [Batch arguments](https://github.com/WarcraftXL/core/blob/f39aa1c9f2020d0968def3de895283cf0412e7cd/src/engine/events/Event.hpp#L133-L148) · [One-shot interface](https://github.com/WarcraftXL/core/blob/f39aa1c9f2020d0968def3de895283cf0412e7cd/include/wxl/M2DrawApi.h#L22-L31) · [v1.2 event ownership](https://github.com/WarcraftXL/core/blob/2a9132b0306380b632e51b594b8c066a9af0af24/include/wxl/events/Events.def#L29-L56)
* **Native Vulkan.** Esteria's Gx device resolves bound vertex and index pools, reads the batch range, flushes current shader registers, builds bindings and submits a draw. Its interface lives inside a rebuilt client. The installed client calls D3D9 and uses DXVK. The semantic inputs are available above either backend. Generating matching per-pixel normal, depth and alpha coverage remains a separate render operation. The existing Northlight MSAA fusion experiment has image and timing results relevant to changing that operation. [Vulkan draw](https://github.com/STRHercules/wowdecomp/blob/4ed9b35d64aad63b654e6961a00b63739045635e/Engine/Source/Gx/CGxDeviceVulkan/CGxDeviceVulkanDraw.cpp#L74-L201) · [Northlight MSAA experiment](msaa-worldnormals-fusion-20261114.md)

## Verification against the installed game

Offline disassembly of the installed PE32 `Wow.exe` (3.3.5.12340, SHA-256 `99155d4d6ed4937a5ab1f5972d11e8605b986561b9f08686ab66af2c582194ec`) confirmed two scene-to-dispatch calls, separate ordinary and grouped-doodad branches, current-element batch/section loads, the bone-combination lookup into the instance palette, the c31 upload and the indexed section fields at Gx submission. The five byte regions inspected also matched the installation's `Wow_original.exe`. This verifies selected code paths on disk. The log contains aggregate draw counters and no per-draw native model/section IDs, so it cannot establish runtime matching coverage.

## First integration for the existing client

1. Observe ordinary opaque M2 batches on the game thread as the engine submits them. Reuse the existing CPU/GPU source identity and buffer generation for the active section. Cache immutable section metadata per loaded skin/LOD, and share the exact emitted palette rows per pose and bone combination. This naturally follows visibility and draw order during the engine's own traversal. Reading the scene again at frame end would lose that ordering and repeat work.
2. Attach the metadata reference to the **specific device draw** as the command producer records it. Include the pass, generation and section range. Transfer owned data or a frame-lifetime reference across the queue. The live log used separate game and replay threads with two frames ahead configured. A later read of an engine pointer can observe a recycled model, a newer pose or another pass. The existing producer already associates camera/light snapshots with a draw ordinal. [Snapshot capture](../src/stream/game_snapshot.h) · [Per-draw capture](../src/proxy/renderer.cpp)
3. First run the association alongside the existing path and compare section draw arguments, buffer identity, palette rows and actual material/alpha state for the same command. Count eligible, matched, ambiguous and fallback draws. Grouped instances, UP/dynamic geometry, projected passes and missing metadata keep their existing capture until separately supported. An off-screen caster can still affect a visible receiver, so the camera pass's visible list alone cannot establish shadow eligibility.
4. First consume matched records in material admission and model-normal packet preparation. Compare producer and replay CPU time, total frame time, normal/material images and actual GPU submissions on the same input. This measures whether CPU work disappears or moves between threads. Reducing the remaining normal draws requires a compatible GPU pass or batching improvement in addition to the CPU integration.

## Implemented for ordinary opaque M2

On sampled diagnostic frames the command-stream producer recognizes the indexed shader batch in build 12340. It checks three executable code regions at startup. On submission it checks both callers, the scene pass and material, active D3D bindings, alpha state and the final draw range including Gx pool offsets. A match adds 16 bytes to that draw. They describe the instance, section, material and bone selection. Replay treats the identity words as opaque. The existing ordered shader-constant commands own the actual palette values. Other draws retain their ordinary D3D packet. [Client adapter](../src/stream/m2_draw_12340.h)

For normals, a draw can copy constants directly from the material calculation when the requested span is covered and the device mirror certifies its write generation under the draw lock. Queued packets retain their own storage. In the November 18 Northrend recording the producer recognized 28,214 ordinary draws in the diagnostic samples. All 1,781 sampled native palettes and 26 sampled normal constant spans matched their reference reads. Across the selected enabled intervals the reported median register reads fell from 160,431 to 43,566. The crowd and submission counts changed between recordings, so these counts measure avoided reads only. [Normal packets](../src/proxy/model_normal_renderer.h)

An experimental last-pose cache for material bounds hit twice in 9,073 sampled evaluations. It avoided zero coarse range queries. The build after that recording removes the comparisons and per-mesh storage. `NATIVE_M2` reports producer matches. `MODEL_NORMALS handoff` (previously `NATIVE_M2_NORMALS`) reports reused constant spans and sampled comparisons with a fresh device read. The receiver accepts a loan for the same non-UP draw when its requested rows are covered and the held device mirror certifies the generation. This proof is independent of the engine caller. The stock-client section decoder now runs on the existing 1-in-127 diagnostic cadence.

## Cold entry in the same recording

From the first Northrend camera sample to the static geometry transition, 15.969 seconds elapsed. The CPU region build reported 9.110 seconds. GPU staging reported 6.688 seconds over 192 visits for 242 pages, 1,367 material slots and 180 new textures. The CPU had published a solved GI snapshot by 9.250 seconds. The previous renderer held its atlas until the static mesh was drawable. Screen lighting and weather had separate readiness conditions.

The renderer can now publish a complete GI atlas for the current map while the static mesh is staging. Device reset or incomplete writes invalidate the atlas serial. The first successful upload logs `WORLD probe atlas ready` with the map, tick and static mesh status. Material references retain their own cutoffs and share their owner's texture. The per-visit limit applies to new textures, and all staging remains subject to the existing deadline and byte budget. Spool reads copy consecutive rows together, and the temporary file seeks on direction or position changes. [World renderer](../src/world/world_renderer.h) · [Temporary storage](../src/gi/temporary_geometry.h)

On the next recorded entry (build `349114c5`), the atlas was available after 24.875 seconds, with actual probe shading sampled before the static mesh became drawable at 27.812 seconds. The worker built the same 1,582,232-triangle local region four times. Downstream shadow scratch repeatedly reached the in-memory builder's 384 MiB admission floor. The worker reported a 19.828 second memory-stall episode. A shadow allocation refusal now retries the unfinished stages with file-backed scratch while retaining the completed local BVH. Healthy regions keep the in-memory path. A local allocation refusal can enter the existing bounded local builder as soon as its entry budget admits the retry. The file-backed stages use their own per-allocation checks, including the 256 MiB process reserve. Resident replacement pages are rechecked under the worker mutex before elision.

In that recording, complete focused 120-frame intervals starting two seconds after geometry readiness or a toggle averaged 33.10, 13.76 and 32.91 ms in the enabled, disabled and re-enabled periods (360, 1,080 and 360 frames). In the six sampled enabled frames, median net CPU capture was 7.97 ms. Median source readback bytes were zero for material geometry and model normals. Model normals still submitted a median of 1,202 draws with MSAA. These measurements apply to this recording.

Two paired cold-entry runs per memory budget used the x86 worker, Northrend cache and client DXVK, reversing build order for the second run. At 825 MiB of available address space, GI readiness improved from 6.17–6.27 s to 3.38–3.48 s, with one completed local build instead of two. Static pages were ready in 4.14–5.00 s versus 6.98–7.84 s. At 740 MiB, GI improved from 5.28–5.30 s to 4.39–4.44 s. At 980 MiB the GI and static times changed by at most 0.10 s. At 1,575 MiB GI took 0.08–0.13 s longer, and static readiness took 0.50–0.61 s longer, with more GPU upload visits. All 16 runs produced the same page digest, 2,730,126 triangles and 236 pages at 1,120 units of reach. Live entry times and steady-state frame cost for the installed build require a new recording.

## Shadow material memory

The next live Northrend entry (source `80177166`) built its local BVH once. From the first world camera, GI was ready at 3.984 s and static shadows at 7.421 s. The extended shadow build encountered 374 MiB free against its 384 MiB admission floor and retried at 1,120 units of reach instead of 2,048. Static staging took 3.422 s over 83 frames. In full 120-frame windows beginning at least two seconds after readiness or a toggle, frame times averaged 37.22, 20.24 and 39.11 ms across the on/off/on periods (240, 360 and 120 frames).

Static caster shaders read only alpha. The shadow planner now extracts the original eight alpha bits on the worker, shares masks after checking dimensions and coverage bytes, and represents fully covered images with a single white texel. Material slots retain their authored cutoffs. The GPU uses its opaque path when that texel proves every sample passes. A8 devices upload the coverage directly. Four-channel devices expand it at the final copy. GI continues to sample the source RGB. The worker-entry test compares the complete local mask contents back to the independent GI inputs and checks the resulting page raster. [Worker preparation](../src/world/world_mesh_plan.cpp) · [Cold-entry test](../tests/world_upload_worker_entry.h)

In the 96 MiB free-span fixture, the 1,315 material slots required 29,799,698 bytes of prepared masks and 143 GPU textures, down from 135,058,324 bytes and 164 textures. The coverage check compared 69,642,240 source texels. Both versions produced 236 pages and 2,730,126 triangles at the same reach. These byte counts measure prepared shadow material payloads. The original GI textures and driver allocations have separate lifetimes.

In two paired runs with 1,563 MiB available and a 1,493–1,514 MiB largest free span, both builds retained the full 2,048-unit reach and produced identical page digests across 351 pages and 4,155,627 triangles. After page preparation, the worker accounted for 476.6 MiB, down from 577.0 MiB. GI was ready in 2.922–2.954 s versus 3.094–3.125 s. Static shadows were ready in 3.656–3.688 s versus 4.640–4.781 s. These times cover cold entry in the x86 worker and client DXVK fixture. The frame times above come from the game recording before the coverage change.

## Reusing material bounds for point shadows

On renderer frame 414 in that recording, 713 of 1,808 replay packets had spatial bounds. Twelve point lights submitted 78,375 replay draws. On two later frames with all bounds ready, replay counts were 7,329 and 7,385. The renderer can now fill a missing bound from the material pass when mesh, declaration, shader and captured constant generations match. The packet owns the view-space box. Point shadows transform it with the replay camera and report how many packets used it in `POINT_COLD materialBoundsUsed`. A change to a light's inner attenuation radius also preserves its depth cube.

In a client DXVK fixture with 32 packets and one light, supplying the boxes cut submissions from 192 to 32. All six R32F faces matched exactly. Median GPU time was 0.01694 ms before and 0.00521 ms after, over six measured blocks per mode. On a warm indexed model-normal fixture, retaining sampler state only for stages read by each shader reduced the queue charge for 513 packets from 1,075,248 to 619,704 bytes. These measurements cover the two fixtures. [Point shadow test](../tests/point_shadow_stutter_gpu.cpp) · [Model-normal test](../tests/test_material_pose_handoff_gpu.py)
